**User:** Our volunteers want to publish the sensor data openly on a public dashboard, which I support, but I'm nervous about putting up numbers that I know are biased. If a unit is reading three degrees high because of drift and a local journalist picks it up, that undermines the whole project. Should we hold off until the calibration problem is solved, or publish raw with warnings?

**Assistant:** Many community networks handle this with data quality tiers. Publish raw data for transparency, but clearly separate it from a corrected or quality-controlled product, and display quality flags for each sensor, such as drift suspected, siting non-standard, or recently co-located. Dashboards can default to showing only data that passed basic checks. Including versioned correction methods in documentation also helps, so when you improve the calibration later, you can reprocess historical data and explain the change.

**User:** Tiers make sense. The awkward part is that our corrected tier doesn't really exist yet, because I still don't have a calibration method I'd stand behind. We need someone with stronger stats who can help design the correction properly. Until then I might just publish raw with flags and a big note that a calibrated version is coming.

**Assistant:** That is a sensible interim plan. A visible roadmap note can actually help recruit help, since it signals to potential collaborators that there is a concrete, well-defined methods problem with real users waiting. When you approach someone, offer co-authorship on a methods paper and a clear scope, for example a correction pipeline for temperature and fine particulate matter using the reference station and co-location periods, so they can see the size of the commitment.
