**User:** Our group shares a cluster with a few dozen GPUs, and most of our work is lots of small training runs, hyperparameter sweeps and ablations that each use maybe a quarter of a GPU's memory. The default scheduler gives each job a whole GPU, so utilisation was terrible. I ended up writing my own scheduler layer that packs several small jobs onto one GPU based on their measured memory and compute footprint. Are there pitfalls I should watch for?

**Assistant:** Packing small jobs is a good idea and many groups have done something similar. Main pitfalls: memory estimates can be wrong if jobs have variable batch sizes or memory spikes during evaluation, which causes out-of-memory errors that kill co-located jobs; compute contention can slow each job more than you expect, so total throughput may rise while individual job latency gets worse; and isolation is weak, so a misbehaving job can affect others. Approaches like hardware partitioning on GPUs that support it, or memory caps per process, can help, along with a short profiling run to measure each job's footprint before placement.

**User:** I already do a short profiling pass, the scheduler runs each job for a couple of minutes alone, records peak memory and SM utilisation, then bin-packs with a safety margin. Average GPU utilisation went from around 30 percent to over 75 percent and our sweep turnaround dropped a lot. A couple of other labs in the building have asked about it. I'd like to clean it up enough to share, but I'm not sure what documentation people would actually need.

**Assistant:** Those are strong results and very shareable. For adoption, people usually need: a quick-start that runs on a single node with a toy workload, an explanation of the profiling and packing logic including the safety margin and how to tune it, a list of assumptions such as supported GPU types and cluster managers, failure modes and how jobs are rescheduled after an out-of-memory error, and a brief summary of your before-and-after utilisation numbers. A short guide for cluster administrators about integrating it with existing fair-share policies would also reduce friction.
