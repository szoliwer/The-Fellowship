**User:** Small issue with my GPU packing scheduler. Occasionally a job's memory spikes way past its profiled peak, usually during validation with larger batches, and it takes down the other jobs sharing the GPU. Right now I use a fixed twenty percent safety margin. Should I make it bigger or is there a smarter approach?

**Assistant:** A bigger margin reduces packing efficiency for everyone to protect against a few jobs. Smarter options: profile across both training and evaluation phases, since validation spikes are predictable if you trigger an evaluation step during profiling; set a per-process memory cap so that a spiking job fails alone rather than killing neighbours; implement automatic checkpoint-and-restart so a failed job is requeued on a less crowded GPU with a higher memory estimate; and learn per-job-type margins from history, since repeated runs in a sweep behave similarly.

**User:** Profiling an eval step is an obvious fix I somehow missed. I already have checkpoint-and-restart, so adding the per-process cap plus a history-based margin should cover most cases. Honestly this is the kind of practical detail I'd want to pass along to the other labs when I share the tool, because they'll all hit it within a week.

**Assistant:** Definitely worth including. A troubleshooting section built from real incidents is often the most valuable part of internal tooling docs. You could also ship sensible defaults, such as profiling with an evaluation step enabled and a modest default cap, so new users avoid the problem without reading anything. Logging which jobs triggered restarts and why will help both you and adopters tune the margins.
